**Goal:** Deploy the existing service image as a public Hugging Face Space with the demo page as its UI (the challenge's optional deliverable D6), close the measured gap between host and container latency as far as a thread-count setting can, verify the live Space with the project's own checks, and put the link and the measured numbers into the report, so the author can send the link in a follow-up e-mail.

**Architecture:** The Space is a Docker Space built from this repository pushed as-is to the Space's git remote: the Dockerfile at the root is the Space's build, the README's YAML front matter declares `sdk: docker` and `app_port: 8000`, and the image already serves the demo page at `/`. Spaces run every container as user ID 1000 and inject Space variables as environment, so the image's user becomes uid 1000 and `HF_HOME` points at a writable path. Before deploying, one experiment on the local container measures the served model's latency at several torch thread counts and the best setting goes into the image as a default (`NF_TORCH_THREADS`), recorded as decision 0011. After the author creates the Space and pushes, the live URL is checked with `scripts/container_check.py --url` (the same example check, with the known mismatch expected) and benchmarked with `scripts/bench.py --url`, and the report gains the link and the Space row.

**Tech Stack:** Docker (the existing image), Hugging Face Spaces (Docker SDK, free CPU hardware: 2 vCPU, 16 GB), git push to the Space remote, `huggingface_hub` for the author's Space creation, the existing `scripts/container_check.py`, `scripts/bench.py`, `scripts/report_tables.py`.

**Spec:** `docs/02-design.md` 6.1 (`GET /` "is the UI for the Hugging Face Space; the Space runs the same image"), 6.4 (ONNX only if the latency target is missed), 9 (M6 row: "Space deployed; further items only while a measured number improves"); `docs/01-requirements.md` D6 (optional, encouraged: deployed service with a minimal UI, link in the report), Q1 (latency measured and reported); decision 0010 (container p50 342.9 ms against the 92.8 ms host figure, cause untested, the thread-count experiment named as the M6 route); the Hugging Face Docker Spaces documentation (front matter keys `sdk: docker`, `app_port`; "The container runs with user ID 1000"; variables injected at runtime; `--chown` on copies, no recursive chown).

## Review Focus

Inputs the spec implies but that no section spells out, each pinned by a check in the task that owns it:

1. **The Space's user is not the image's user.** Spaces run as uid 1000; the image sets uid 10001. Every file the service reads must be readable by uid 1000 and the service must not write anywhere but `/tmp`. Task 2 aligns the image user to uid 1000 and runs the local container as `--user 1000` to prove the service starts and serves either way.
2. **Transformers and Hugging Face libraries write caches.** Loading from a local directory still touches `HF_HOME`; with an unwritable home the load may warn or fail. Task 2 sets `HF_HOME=/tmp/hf` in the image and the `--user 1000` run proves the load.
3. **A thread setting that helps on one machine can hurt on another.** The Docker Desktop VM has 8 vCPUs here; the free Space has 2. Task 1 measures 1, 2, 4 and the default, picks by the container p50 at 2,000 characters, and Task 3 measures the Space itself; the report shows both so a reader sees the setting's effect on each.
4. **A public endpoint with no authentication.** Design 6.1 specifies an open demo API, but the Space is on the public internet. Task 3 sets `NF_MAX_CHARS=20000` as a Space variable (the author's step) and the report says the demo is rate-limited only by the Space's hardware; the service already rejects oversized bodies early (M3).
5. **Free Spaces sleep after inactivity** and take a minute to wake. The report's link paragraph says so, and `container_check.py --url` waits up to three minutes for health. Task 2 (the wait) and Task 3 (the sentence).
